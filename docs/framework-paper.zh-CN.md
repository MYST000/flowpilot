# FlowPilot：面向工具增强智能体工作流的时序感知复用与推理调度

*FlowPilot: Temporally Aware Reuse and Inference Scheduling for Tool-Augmented Agent Workflows*

## 摘要

工具增强智能体通过交替执行语言模型推理与外部工具调用推进任务。这一执行方式使推理请求的到达时间、可复用上下文以及工作流剩余时限相互关联：工具结果复用可以提前释放后继请求，而工具执行期间的 KV 状态保留又会影响后继请求的计算成本。为协调上述关系，本文提出 FlowPilot，一个连接智能体运行时与推理引擎的工作流感知框架。FlowPilot 以动态线路前沿刻画当前执行进度，通过具备来源验证的工具结果复用与在途调用合并形成后继需求时间估计，并据此选择已完成推理状态的保留、卸载或释放方式。当后继请求实际形成后，框架查询其可用前缀，结合经标定的预填充与数据传输成本，按照剩余预填充裕量进行单实例准入调度。该设计在保持运行时对工具执行和对话历史的权威性的同时，将应用侧需求与引擎侧状态成本连接起来。本文给出框架模型、核心机制及原型适用范围，以服务等级目标内完成的工作流数量为主要优化目标。

**关键词：** 工具增强智能体；工作流调度；工具结果复用；前缀缓存；KV 状态管理

## 1. 研究动机

一个工具增强智能体任务通常跨越多轮推理。模型首先根据已有上下文生成工具调用，运行时执行工具并写入观察结果，随后模型利用扩展后的上下文继续推理。因而，推理服务所接收的一组请求，实际上可能属于同一任务在不同时刻的推进过程。请求之间既共享历史上下文，也通过工具结果和跨线路等待关系形成时序约束。

这种执行方式带来两个相互关联的问题。首先，后继请求的形成时间取决于工具结果的获得方式。同一搜索请求可能从历史缓存立即返回，也可能等待另一个调用的真实执行结果，还可能需要完整执行一次本地工具。其次，即使两个后继请求具有相近的上下文长度，其推理成本仍可能不同：一个请求的前缀驻留于 GPU，另一个仅保留 CPU 副本，还有一个需要重新计算。因此，工具阶段的等待时间和推理阶段的状态可用性需要在同一工作流语境下理解。

例如，两条线路刚刚完成推理，并分别发起页面读取和外部搜索。若页面读取命中已有结果，其下一轮推理可能很快形成；此时继续保留 GPU 前缀有助于减少后继计算。若搜索仍需等待较长时间，暂时将相关状态转移到 CPU 则可能释放 GPU 空间，供其他已就绪请求使用。一旦搜索命中历史结果，原先较长的等待窗口会立即缩短，之前的状态保留判断也需要重新评估。由此可见，工具复用既减少重复执行，也会改变推理状态再次被使用的时间。

FlowPilot 围绕这一联系组织系统设计。框架通过当前工作流前沿关联工具事实与推理请求，在响应完成时处理未来状态需求，在完整请求到达时处理实际计算成本。前一阶段依据已知事实形成条件估计，后一阶段利用真实请求修正估计，使两个决策时刻具有明确的信息边界。

本文的设计贡献集中于三个方面：以动态线路前沿表达当前推进位置与真实等待关系，为跨阶段决策提供共同的工作流语境；将工具结果复用转化为可更新的后继需求时间，使 KV 保留能够响应工具阶段的变化；将目标前缀观察转化为条件计算成本，并以剩余预填充裕量协调完整请求的派发。这三个部分共同构成从工具事实、状态价值到请求次序的决策链。

## 2. 问题建模

### 2.1 工作流与在线执行前沿

设工作流集合为 $\mathcal{J}$。每个工作流 $J_j$ 具有起始时刻 $s_j$、可选截止时刻 $d_j$，以及一组可独立推进的执行线路 $\mathcal{L}_j$。一条线路对应一个持续演进的会话，其内部反复经历推理、工具结果解析与后继请求形成。子智能体可以创建新的线路，并继承原工作流身份。

在时刻 $t$，令 $\mathcal{L}_j(t)$ 为当前维护的线路集合，$\mathcal{E}_j(t)$ 为运行时明确报告的等待关系。边 $(\ell_a,\ell_b)\in\mathcal{E}_j(t)$ 表示线路 $\ell_a$ 的继续推进依赖线路 $\ell_b$。父子会话关系只描述来源；只有实际等待才形成依赖边。工具调用属于当前推理回复中的结构化内容，不单独扩展为工作流图节点。

FlowPilot 维护在线前沿

$$
\mathcal{F}_j(t)=
\left(\{\tau_\ell(t):\ell\in\mathcal{L}_j(t)\},\mathcal{E}_j(t)\right),
$$

其中 $\tau_\ell$ 是线路当前尾部，包含当前请求引用、上下文位置、版本和执行阶段。完整对话历史由智能体运行时保存。每条线路的尾部记录保持有界，尾部及显式依赖结构的规模随当前线路数与依赖数增长；工具缓存、请求记录和未确认上下文增量具有独立生命周期。

### 2.2 优化目标

设工作流 $J_j$ 的实际完成时刻为 $f_j$，评价窗口长度为 $\Delta T$，$\mathcal{J}_{\Delta T}$ 为在该窗口内完成且规定了截止时间的工作流集合。本文采用 SLO 有效吞吐（goodput）作为主要目标：

$$
G_{\mathrm{SLO}}=
\frac{1}{\Delta T}
\sum_{j\in\mathcal{J}_{\Delta T}}
\mathbf{1}\{J_j\text{ 成功完成且 }f_j\leq d_j\}.
$$

在此基础上，考察加权任务完成时间 $\sum_j w_j(f_j-s_j)/\sum_j w_j$、重复工具执行和 KV 恢复或重算开销。这里的 $w_j$ 是评价目标中的任务权重，不意味着原型的每个调度分支都实现了相应的加权最优化。缓存命中率和请求吞吐用于解释性能变化，工作流是否按时完成则决定主要收益。

这一目标面对部分可观测的在线环境：未来工具调用尚未确定，工具输出会改变后继请求内容，缓存状态也可能在观察后变化。FlowPilot 因而采用由事实驱动的分阶段启发式决策，并在后继请求到达时重新观察其成本。

## 3. 框架概览

FlowPilot 位于 OpenHands 与一个固定的 vLLM 实例之间。OpenHands 维护智能体循环、真实工具执行和权威对话历史；FlowPilot 维护执行前沿、复用决策、外部准入队列与状态保留偏好；vLLM 维护 KV 物理状态，并执行实际推理、恢复或重算。三者通过请求身份、工具生命周期事件和引擎状态观察建立关联。

```text
 +---------------------------------------------------------------+
 | OpenHands                                                     |
 | Agent loop | Authoritative history | Local tool execution      |
 +---------------------------------------------------------------+
          | complete requests / tool facts       ^ replies / reuse
          v                                      |
 +---------------------------------------------------------------+
 | FlowPilot                                                     |
 |                                                               |
 |  Line-tail frontier <--------> Tool reuse and in-flight binding |
 |          |                               |                    |
 |          |                         Successor demand           |
 |          v                               v                    |
 |  Single admission queue         KV retention policy           |
 |          ^                               |                    |
 |  Target-prefix cost                      |                    |
 +---------------------------------------------------------------+
       | ordinary requests      | query / KEEP / OFFLOAD / DROP
       v                        v
 +---------------------------------------------------------------+
 | One vLLM instance                                             |
 | Prefix validation | KV storage | Restore / recompute | Inference|
 +---------------------------------------------------------------+
```

**图 1.** FlowPilot 的系统结构。工具事实决定后继需求时间；引擎前缀观察决定已形成请求的条件计算成本。

框架的协调过程围绕相邻两轮推理展开。当前回复产生完整工具调用后，FlowPilot 解析复用机会，并根据实际解析结果与执行事件更新后继需求。此时，状态保留策略决定当前 KV 在工具阶段的存放方式。待工具、依赖与上下文条件满足，完整后继请求进入单实例队列；目标前缀查询提供当前计算成本，调度器结合剩余时限决定派发次序。这一过程使工具复用、状态保留和请求排序共享工作流语义，同时保持各自的执行职责。

## 4. 动态线路前沿

FlowPilot 使用线路尾部表示每条会话的当前推进位置。尾部具有空闲、活跃、阻塞、就绪和终止五种阶段，分别对应 `EMPTY`、`ACTIVE`、`BLOCKED`、`READY` 和 `TERMINAL`。合法完整请求到达后，系统以新请求替换当前尾部并进入活跃阶段；回复完成后，若仍存在工具、依赖或上下文屏障，则进入阻塞阶段，否则进入就绪阶段。普通回复完成只意味着线路能够继续推进，工作流结束由显式终止语义确定。

每次尾部替换和依赖更新均与版本关联。依赖集合以原子方式替换，并校验同一工作流约束和无环性。请求派发及状态保留动作执行前，系统重新核对当前尾部身份，避免较早请求的异步结果作用于已经推进的线路。逻辑请求、传输尝试和具体模型调用分别标识，使失败重试能够保持任务语义，同时区分每次真实上游调用。

该表示将“当前谁在等待谁”与“过去发生过什么”分开。前者直接支持就绪判断和阻塞线路统计，后者保留在运行时历史及相应记录中。它也限制了预测信息的作用范围：尚未出现的工具调用不会创建依赖，父子会话关系不会自动变成等待关系。由此，调度所依赖的结构始终来自已经发生的执行事实。

## 5. 工具复用与后继需求时间

### 5.1 具有来源约束的结果复用

FlowPilot 针对显式注册且获运行时授权的工具建立复用描述。对工具调用 $u$，可将其描述抽象为

$$
K(u)=\bigl(\sigma_u,N_u(a_u)\bigr),
$$

其中 $a_u$ 为实际参数，$N_u$ 为工具适配器定义的规范化过程，$\sigma_u$ 汇集工具族、版本、结果结构、部署域及复用策略等硬约束。精确复用要求完整描述一致，并通过有效期和交付条件检查。规范化具有工具专属性，例如受限 URL 读取可以规范化主机名，但不会据此任意改写查询参数或命令语义。

解析过程首先查询精确历史结果；对于明确允许语义复用的工具，再查询相同硬约束下的语义候选。若历史结果不可用，则查询精确在途绑定，以及被允许的语义在途绑定。最终仍未匹配的调用登记为新的执行者，并由 OpenHands 完成真实工具执行。历史复用消除已完成工作的重复执行，在途合并则使兼容调用共享一个尚未完成的执行结果。

在途绑定针对已经登记的调用意图建立。首个调用作为执行者，后续兼容调用作为等待者；匹配与执行者登记在同一临界区完成。执行结果只有在真实执行事件通过验证、且运行时已提交对应观察后才可发布。交付给等待者时，系统保留来源信息，并使用等待者自身的工具调用标识构造观察。因此，结果内容可以复用，而会话身份与消息顺序仍属于各自线路。

语义复用只放宽工具策略允许的查询内容，其他约束保持一致。原型提供旁路观测、候选提示和主动替换三种模式；其中前两种模式继续进行本地执行。主动替换依赖独立的质量验证，查询相似度本身不能证明结果或证据等价。

### 5.2 从复用决策到需求时间

工具复用对调度的影响通过后继需求时间体现。对于线路 $\ell$，定义 $\widehat T_{\mathrm{need},\ell}$ 为依据当前工具解析状态估计的后继需求时刻，相应等待窗口为

$$
g_\ell(t)=\max\bigl(0,\widehat T_{\mathrm{need},\ell}-t\bigr).
$$

历史结果可交付时，相关工具等待可以解除；在途等待者依赖执行者的真实发布；本地执行则依据已开始时间与可用时延估计更新剩余等待。当前运行时按回复中的顺序串行执行多个真实工具，因此尚未开始的本地调用需要累加持续时间，已经开始的调用只计算预计剩余部分。在途结果的绝对就绪时刻可以与这一过程重叠。存在未知工具时延或尚未解决的跨线路依赖时，需求时间保留为未知。

需求时间用于估计状态何时可能再次被使用，实际队列资格仍由工具完成、依赖解除及上下文一致性共同决定。工具等待中的线路不作为一个虚拟推理请求占据准入队列。

框架还提供异步预测接口，可接收工具族概率与时延分位数，用于元数据预热，以及实际未命中后的有界时间先验。预测与推理转发并行进行，完整工具调用到达后由事实覆盖预测。当前原型提供接口与回放能力，未内置经过生产校准的预测模型；上述基本机制可以独立于预测运行。

### 5.3 独立的工具缓存容量

工具结果缓存具有独立于 KV 缓存的容量预算。其保留启发式综合真实执行时延、复用次数、剩余有效期和载荷大小，使容量优先服务于能够节省较多重复工作的结果。过期结果首先移除，正在交付的结果受到暂时的容量保护。

当前有效期策略在成功复用后按原窗口滑动续期。续期更新结果的可交付期限，保留最初观察时间和执行来源；它不代表重新访问外部数据。因此，具体工具是否适合这种有效期语义，属于注册时声明的复用假设。

## 6. 面向后继需求的 KV 状态保留

### 6.1 两个决策时刻的信息差异

一轮推理结束后，FlowPilot 可以关联该轮已完成计算的 KV 描述，并观察其当前可用范围，但下一轮工具输出和完整输入尚未形成。此时的保留决策针对已知前缀的后续使用价值。完整后继请求到达后，系统才能通过实际渲染和分词查询真实目标前缀。

这一差异决定了两种观察的用途：完成请求的描述用于管理已有状态，目标请求的查询用于估计实际计算成本。即使对话只是追加内容，模板重渲染也可能改变 token 前缀，因而旧描述无法单独证明新请求具有相同的可复用范围。

### 6.2 保留、卸载与释放

FlowPilot 为已完成推理状态考虑三个动作：`KEEP` 表达 GPU 保留偏好，`OFFLOAD` 请求建立或复用 CPU 副本并安全回收可释放的 GPU 映射，`DROP` 撤销当前拥有者的状态需求并请求安全释放。物理引用、共享前缀、复制完成及回收条件由引擎判定。`KEEP` 是软保留偏好，驻留保证需要引擎实际持有保护引用；异步动作的接收也与其最终完成相区分。

当后继等待窗口和兼容成本模型均可用时，策略比较各动作的预计后继计算成本及状态持有代价。令 $\widetilde P_\ell$ 为已知前缀长度加一个后继 token，用来表达响应时刻的条件续接假设；令 $H_g$ 为当前 GPU 可用前缀，$H_o$ 为合法 CPU 卸载目标所覆盖的前缀。记 $\widehat F(P,H)$ 为利用长度 $H$ 的前缀后预计的残余预填充时间，$\widehat T_{D2H}(b)$ 与 $\widehat T_{H2D}(b)$ 为真实对象字节数 $b$ 对应的传输时间估计。

各动作的后继阶段成本为

$$
\begin{aligned}
u_{\mathrm{KEEP}} &= \widehat F(\widetilde P_\ell,H_g),\\
u_{\mathrm{OFFLOAD}} &= \widehat T_{H2D}(b_c)
  +\widehat F(\widetilde P_\ell,H_o),\\
u_{\mathrm{DROP}} &= \widehat F(\widetilde P_\ell,0).
\end{aligned}
$$

这里的 $H_o$ 截断在 $\widetilde P_\ell$ 范围内。卸载只有在引擎支持对应能力、成本可估计且 $\widehat T_{D2H}(b_c)\leq g_\ell$ 时，才进入这一成本比较，以避免假设尚未完成的复制能够被后继请求使用。

令 $B_g$ 和 $B_c$ 为引擎报告的对象容量换算成 GiB 后的数值，$\lambda_g$ 和 $\lambda_c$ 为将单位容量持有时间折算为策略代价的参数，则

$$
\begin{aligned}
v_{\mathrm{KEEP}} &= u_{\mathrm{KEEP}}+\lambda_g B_g g_\ell,\\
v_{\mathrm{OFFLOAD}} &= u_{\mathrm{OFFLOAD}}
  +\widehat T_{D2H}(b_c)+\lambda_c B_c g_\ell,\\
v_{\mathrm{DROP}} &= u_{\mathrm{DROP}}.
\end{aligned}
$$

GPU 压力较大时提高 $\lambda_g$。设线路剩余时限为 $R_\ell$，策略在可比较动作集合 $\mathcal A_\ell$ 中选择

$$
x_\ell^*=\mathop{\arg\min}_{x\in\mathcal A_\ell}^{\mathrm{lex}}
\left(
  [u_x-(R_\ell-g_\ell)]_+,
  v_x
\right),
$$

其中 $[z]_+=\max(0,z)$，$\mathrm{lex}$ 表示字典序比较。该规则先比较相对于后继阶段预算的预计超支，再比较计算、传输与状态持有代价。没有截止时间时，仅使用第二项。

上述计算使用已知前缀的条件续接模型，实际工具输出长度与未来请求内容仍待后继到达后确定。对象容量也可能包含被其他线路共享的块，因此该规则是局部保留启发式，不等价于对全局边际显存收益的精确求解。

无法获得兼容标定或等待时间时，原型显式采用需求距离与容量规则：近期需要且无 GPU 压力时优先保留，否则在能力允许时卸载。已终止线路或经确认没有可恢复前缀的状态优先释放。未知可恢复范围不会被解释成零。

### 6.3 将恢复执行留在推理引擎

状态保留决定工具阶段如何持有已有计算，实际恢复则属于后继推理的一部分。后继请求即使只有 CPU 前缀，也可以按照普通请求进入 vLLM。引擎重新验证输入、获取引用，并自主选择恢复或重算。

FlowPilot 通过普通请求提交保持这一执行路径：外部队列不建立 GPU 就绪屏障，条件恢复成本只参与外部排序与保留价值比较。这样，应用侧时序信息可以影响资源需求表达，而引擎仍能依据最新物理状态完成最终执行决策。

## 7. 基于剩余预填充裕量的准入调度

### 7.1 真实目标前缀与条件成本

对于已经形成的完整请求 $q$，设其输入长度为 $P_q$，当前 GPU 可消费前缀为 $H_q^g$，引擎能够通过兼容 GPU/CPU 路径利用的候选前缀为 $H_q^a$。当观察完整时，有

$$
0\leq H_q^g\leq H_q^a\leq P_q.
$$

$H_q^a$ 表示一条合法加载路径上的连续可用范围，不能通过 GPU 与 CPU 命中长度直接相加得到。对于混合模型，查询还需要满足全部必需缓存组及有效检查点的要求。查询使用实际目标请求的渲染、分词和引擎缓存标识，其结果只描述观察时刻的状态。

原型按总上下文长度分桶标定预填充时间，在匹配桶内使用

$$
\widehat F(P,H)=\alpha_k+\beta_k(P-H),
$$

并分别标定两个传输方向的固定开销与每字节成本。每份标定记录来源、时间、版本、适用引擎身份和不确定性；传输字节数来自真实对象信息。

据此，请求的两个条件成本为

$$
\begin{aligned}
\widehat C_q^g &= \widehat F(P_q,H_q^g),\\
\widehat C_q^c &= \widehat T_{H2D}(b_q)
  +\widehat F(P_q,H_q^a).
\end{aligned}
$$

当 CPU 候选及标定均可用时，采用 $\widehat C_q=\min(\widehat C_q^g,\widehat C_q^c)$ 作为排序依据；否则使用可用的 GPU 前缀下重算估计。这一最小值表达候选执行方式的条件成本，引擎仍保留实际计划选择权。它不包含 decode、网络或引擎内部排队时间。

### 7.2 剩余裕量

令请求到达时刻为 $a_q$，所属工作流起始时刻为 $s_j$。请求入队时固定已经消耗的工作流时间

$$
CP_q=\max(0,a_q-s_j),
$$

并单独维护等待年龄 $Age_q(t)=t-a_q$。请求采用的截止时刻 $d_q$ 来自线路显式设置，未设置时继承工作流截止时刻。其剩余时间预算和预填充裕量分别为

$$
R_q(t)=d_q-s_j-CP_q-Age_q(t),\qquad
L_q(t)=R_q(t)-\widehat C_q.
$$

$L_q$ 越小，表示在当前条件成本下留给调度器的等待余地越少。FlowPilot 优先派发较小裕量的请求；在同一比较时刻，这等价于按 $d_q-\widehat C_q$ 升序排序。将过去工作流时间固定在入队时刻，再单独增加排队年龄，可以避免重复计入已经经历的工具等待。

当成本无法可靠估计时，系统明确采用截止时间排序并保留成本未知状态。没有截止时间的请求位于有截止时间的请求之后。同一主键下，可按配置比较所属工作流的在途数量，再比较直接阻塞线路数、等待年龄与到达顺序。当前默认配置不启用工作流在途惩罚，因此这一机制不构成严格的公平份额保证。

### 7.3 单队列与事件驱动刷新

所有完整请求共享一条外部准入队列和一个并发额度账本。设配置额度为 $B$，当前已接纳请求数为 $I(t)$，则可用额度为

$$
free(t)=\max(0,B-I(t)).
$$

该额度限制网关提交的并发请求数，与引擎内部批次容量分别管理。调度器在同一临界区完成请求选择与额度预留，随后在锁外提交普通推理请求。额度覆盖引擎内部恢复、重算和推理，直到该调用终止、取消或提交失败时归还。

请求到达、健康更新、额度归还和依赖变化触发合并刷新。每轮对当前排队请求执行目标前缀查询，再更新仍在队列中的成本投影，并可连续派发多个请求。查询在锁外进行，取消和额度归还无需等待查询完成。原型使用全量队列查询，以便依据本轮观察比较候选请求；其额外查询成本需要在性能评价中单独测量。

前缀观察携带引擎身份、状态版本和本地观测时间，并受有效期约束。过期或不兼容的观察转为显式冷启动或成本未知依据。查询本身不锁住 KV 驻留；普通请求到达引擎后仍重新验证前缀。健康信息失效时停止新准入，已提交请求继续完成。

## 8. 连续执行与上下文一致性

工具复用减少真实执行次数，但一轮复用仍可能涉及运行时与网关之间的往返。对于已获明确授权且只使用精确复用的线路，FlowPilot 提供延迟上下文同步（Deferred Context Synchronization，DCS）：网关将完整的模型回复和复用工具结果组织为合法消息批次，在授权范围内构造后继请求，随后将这些增量交回 OpenHands。

这一机制以明确委托为前提。网关记录有界的待确认增量，运行时按完整模型回复及对应工具结果批次原子应用，然后确认同步位置。上下文 epoch、游标、序列号和链式摘要共同验证连续性。部分批次完成确认后，其余批次仍保持待同步；出现分叉时停止续接，并显式暴露冲突。

当前非流式网关路径只有在首批工具全部获得可延迟交付的精确缓存结果时，才进入内部续接；需要本地执行或首批结果尚未就绪时，控制返回运行时。流式回复保持直接转发，其工具边界由运行时处理。这使 DCS 成为特定条件下减少同步往返的扩展机制，基础复用、需求时间估计与准入调度均可独立运行。

整个执行过程保持三个一致性条件。其一，复用结果与真实执行来源关联，并绑定接收线路自身的工具调用身份。其二，只有满足工具、依赖与上下文条件的完整请求才能进入准入路径。其三，跨轮异步操作必须与当前尾部版本相容，较早调用的结果不能更新已经替换的尾部。运行时由此保留最终历史权威，而网关能够在明确授权和可验证增量的范围内参与连续执行。

## 9. 原型范围与研究边界

当前原型面向 OpenHands 与一个固定的 vLLM 实例，已具备线路前沿、精确与在途工具复用、可选语义复用、DCS、事实需求时间、单队列准入以及 KV 保留与目标前缀成本接口。OpenHands 通过默认关闭的适配器提供动态请求身份和工具边界事件；真实多工具调用采用顺序执行。目标前缀查询与状态保留依赖本地 vLLM 扩展，成本排序还需要与引擎相匹配的离线标定。

本文方法的核心在于把工具阶段的需求时间与推理阶段的状态成本连接起来。工具缓存、GPU KV 与 CPU KV 仍具有各自的物理容量约束；跨阶段协调通过需求时间和成本信息实现。响应时刻的条件续接估计在目标请求到达后被实际观察修正，预测器也不成为基本执行路径的前提。

当前实现仍采用启发式而非全局最优策略。保留代价未精确刻画共享块的全局边际收益，成本模型使用点估计，严格工作流公平与多副本恢复也尚未建立。已有原型与局部验证能够支持机制描述，端到端 SLO 收益则需要在固定模型、资源和 CPU 恢复后端下，对原生前缀缓存、仅保留、仅成本排序和组合策略进行对照，并分别考察工具复用、预测先验及恢复成本项的影响。此类评价应同时报告任务成功质量、SLO 有效吞吐、加权完成时间与真实恢复开销，以检验跨阶段协调是否转化为工作流收益。
